范围：全站（扫描内核 / 前端组件 / 内容与 SEO / 测试与构建）。四个模块并行 review 后，每条 finding 均由独立 verifier 证实或证伪；下列所有条目均为 **CONFIRMED**（含最小复现），未经核实的观感类意见单独放在文末「观察」节。

## P0 — 信任面 / 核心正确性

### 1. 加密 PDF 静默产出假「clean」报告（最严重）
- 证据：`src/lib/scanner/mupdfAdapter.ts:217-289` 从不调用 `doc.needsPassword()`；`src/lib/scanner/scanPdf.ts:10-13` 无任何密码/错误分支。
- 复现：用 pymupdf 生成 AES-256 加密 PDF（含可见文本 + 白色注入文本），走真实 `scanPdf()` 管线，返回 `findings: []`、全零 counts 的正常报告；mupdf 仅向 stderr 打 warning，不抛异常，文本抽取静默返回空串。实际存在的隐藏内容完全没被读到。
- 影响：对一个安全扫描器来说是最坏的失败模式——给用户虚假的安心。比报错严重。
- 改法：`extractDocument()` 开头检查 `doc.needsPassword()`，为真时抛出专门错误（如 `PasswordProtectedError`），前端显示「文件已加密，无法扫描」而非 clean 结论。
- 验证：新增 `encrypted.pdf` fixture（`scripts/make_fixtures.py` 生成）+ 单测断言抛错 + e2e 断言 UI 显示加密提示。

### 2. 「Cancel」期间竞态：第二个文件的扫描被静默覆盖
- 证据：`src/components/Scanner.tsx` — `scan()` 在 line 61 置 `loading` 后、line 64 `await file.arrayBuffer()`，worker 到 line 71 才创建；Cancel 按钮在 `loading` 阶段即可见可点（line 131 `busy` 定义 + line 195-218 渲染分支）；`reset()`（line 114-118）对尚无 worker 的扫描是 no-op，不能取消 in-flight 的 `scan()` promise。
- 复现路径（纯 UI 可达）：大文件扫描 → loading 中点 Cancel → 立即选第二个文件 → 第一个 `scan()` 的 continuation 恢复后 `terminateWorker()`（line 70）杀掉第二个扫描的 worker，并用自己的状态覆盖 UI，第二个扫描静默丢失。
- 改法：加 generation counter（每次 `scan()`/`reset()` 自增，`await` 后与当前值比对，不一致则 return）。约 5 行改动。
- 验证：e2e 模拟 cancel + 立即重传，断言最终报告对应第二个文件。

### 3. 隐私页把 Google Analytics 称为「privacy-respecting」
- 证据：`src/pages/privacy.astro:17-19` 写 "Standard, privacy-respecting site analytics… may be used"；而代码里唯一的 analytics 是 `src/layouts/BaseLayout.astro:15,31-40` 由 `PUBLIC_GA_ID` 门控的 Google gtag.js；全仓 grep 无任何 cookie-consent 机制。
- 现状：`PUBLIC_GA_ID` 未设置，构建产物无 gtag，今天线上行为与文案一致；风险在于哪天设了这个环境变量，隐私页文案立刻失实（GA 设跟踪 cookie、跨站画像，多国 DPA 有 GDPR 不合规裁决），直接打击本站「无上传、无跟踪」的核心信任主张。
- 关联：`README.md:7-17` 的 Privacy model 一节也完全没披露这条 GA 可选路径（README 是怀疑的技术读者第一个看的地方）。
- 改法（三选一，按信任优先排序）：a) 删掉 gtag 集成，隐私页改为「无任何 analytics」；b) 换 cookie-free 的自托管统计（Plausible/GoatCounter 类），文案如实描述；c) 保留 gtag 但把「privacy-respecting」改为如实措辞并在 README 披露。首页 `index.astro:39` 的谨慎措辞可作基准。

## P1 — 检测正确性 / 工程护栏

### 4. CropBox 继承被忽略 → `cropbox_mismatch` 假阴性
- `src/lib/scanner/mupdfAdapter.ts:250` 用 `pobj.get('CropBox')`，而 MediaBox（line 247）用的是 `getInheritable`。CropBox 按 PDF 规范同样可从 `/Pages` 祖先继承。复现：CropBox 只定义在 `/Pages` 节点的 PDF，`get()` 返回 null，静默回落到 mediabox，检测永不触发。
- 改法：改成 `pobj.getInheritable('CropBox')`，一行。加对应 fixture。

### 5. 畸形 rect 数组被 `asNumber()` 静默变 0，而非走 fallback
- `src/lib/scanner/mupdfAdapter.ts:40-44`：`/MediaBox [0 0 /Foo 792]` 这类数组过了长度检查后，Name 对象 `.asNumber()` 返回 0 不抛错，产出退化 rect `[0,0,0,792]`，可能触发假 `cropbox_mismatch` 或掩盖真实几何。
- 改法：map 前逐元素 `isNumber()` 校验，任一不是数字即返回 fallback。

### 6. 非 PDF 文件上传导致 WASM `Document` 句柄泄漏
- `src/lib/scanner/mupdfAdapter.ts:218-222`：`openDocument(...)` 对 PNG 等非 PDF 字节也能成功返回 Document（mupdf 自己嗅探格式），`.asPDF()` 为 null 时中间对象从未 `destroy()`。有 FinalizationRegistry 兜底但不确定性回收；worker 是常驻消息驱动的，反复传非 PDF 会累积。与文件内其余的显式 destroy 纪律不一致。
- 改法：先绑变量，`asPDF()` 为 null 时 `raw.destroy()` 再抛错。

### 7. 前端文件类型校验逻辑与意图不符
- `src/components/Scanner.tsx:45`：`if (file.type && …)` 导致 `file.type` 为空串时整个校验短路跳过——空 type + `.docx` 名的文件直接进 worker，最后只得到笼统的 parse 错误。安全上无害（WASM 解析失败兜底），但校验意图未实现。
- 改法：`if (!(file.type === 'application/pdf' || file.name.toLowerCase().endsWith('.pdf')))`。

### 8. 无 CI、无安全响应头
- 全仓无 `.github/workflows`、无任何 CI 配置：`test/build/e2e` 全靠手跑，回归可以无声上 main。建议加一个最小 GitHub Actions：`pnpm test && pnpm build && pnpm e2e`。
- `public/` 无 `_headers`（Cloudflare Pages 的头注入机制），无任何 CSP。本站核心主张「文件不出浏览器」目前只有一条 e2e 测试守着今天的代码；`Content-Security-Policy: connect-src 'self'`（另加 `default-src 'self'` 等）是浏览器级兜底——即便未来某个被投毒的依赖想外发请求也会被拦。对信任型产品这是高性价比的一层。

### 9. 测试缺口（按价值排序）
- **错误路径零覆盖**：无 `encrypted.pdf`/`corrupt.pdf` fixture（与 P0-1 一起修）；Scanner.tsx 的全部客户端护栏（非 PDF 校验 line 45、0 字节 line 56、>100MB line 49、90s watchdog line 75-81、reset line 114）无任何测试；`vitest.config.ts:5` 是 `environment: 'node'`，目前连组件测试的运行条件都没有。
- **no-upload e2e 只监听 HTTP**：`tests/e2e/scan.spec.ts:30` 只注册 `page.on('request')`，未监听 `page.on('websocket')`——WebSocket 外发通道不在这条「无上传保证」测试的覆盖内。加几行即可补上。
- **10 个检测类别中 7 个从未经 UI 验证**：e2e 只断言 `prompt_injection` 和 `near_white_text` 的渲染，其余类别只有纯函数级单测，ReportView 的条件渲染（page/text/detail/fallback/badge）对它们没有护栏。可用一条参数化 e2e 遍历全部 fixture 补齐。

## P2 — 可用性 / SEO / 打磨

### 10. 键盘与读屏可用性（三条，均已核实）
- 焦点不可见：文件 input 是 `sr-only`（Scanner.tsx:190），label 无 `focus-within` 样式，全仓 grep 无相关规则——键盘用户 Tab 到 dropzone 毫无视觉反馈。改法：label 加 `has-[:focus-visible]:ring-2` 或 `focus-within:` 类。
- 无 aria-live：进度文本（line 198-203）是普通 `<p>`，读屏用户不知道扫描在进行；完成后整棵子树替换、焦点无处安放。改法：进度区加 `role="status"`/`aria-live="polite"`，done 时把焦点移到报告标题。
- 报告里「strong signal」只有琥珀色左边框（ReportView.tsx:8-12,86-90），色盲用户无法区分；首页却有文字徽章（index.astro:128-132）。改法：把首页的 "Strong signal" 文字徽章搬进 `CategoryGroup`。

### 11. 分享与品牌资产整体缺失
- 无 favicon（`public/` 只有 robots.txt，BaseLayout 无 `<link rel="icon">`）——每次页面加载都 404 一次。
- 无 `og:image`/`twitter:image`（BaseLayout.astro:25-29 只有 summary card）——所有社交/IM 分享无预览图，对信任型产品的点击率影响实在。
- JSON-LD（index.astro:52-60 的 SoftwareApplication、learn/[slug].astro:24-33 的 Article）均缺 `image` 属性。
- 改法：做一张 og 图 + favicon 套件，三处一起接上。

### 12. Learn 板块 SEO
- 四篇文章互链为零（每篇唯一站内链接都是指向 `/` 的那一条），主题明明强相关（"10 Places" 枚举的类别就是其他三篇的展开）。改法：每篇文末加 2-3 条相关文章链接。
- 三处 meta description 超长会被 SERP 截断：`white-font-resume-trick.md` 173 字符、`10-places-…md` 182 字符、`learn/index.astro:17` 161 字符（阈值约 155-160）。
- `about.astro:19-23` 只列了 10 个检测类别中的 8 个（漏 off-page text 和 annotations），与首页和文章不一致。

### 13. 检测内核小项
- `truncate()`（detect.ts:43-45）和注入上下文切片（patterns.ts:107-113）按 UTF-16 code unit 切，可把 emoji 切成孤立代理项（已复现产生 U+FFFD）。改法：用 `Intl.Segmenter` 或至少切完检查尾字符。
- `InjectionHit.context`（patterns.ts:18-23,104-115）每次命中都计算 ±40 字符片段，但 `src/` 内无任何消费者（只有测试引用）。要么在 ReportView 里展示它（其实对用户有用），要么删掉。
- 每条 annotation 无条件成 finding（detect.ts:89-97，不过滤空 content）——普通高亮/形状批注会灌噪音。与 Python 参考实现行为一致，属继承的已知限制，可考虑过滤空 content 或降噪。

## 已知/接受的限制（不进改进计划，记录在案）
- `isOutsideCropbox` 坐标系不一致（detect.ts:74-78 vs raw cropbox）：代码注释（detect.ts:62-73）和 `tests/fixtures/EXPECTED.md` 已自我记录该检查实际不可达（mupdf 抽取前已按 cropbox 裁剪）。核实确认属实。若日后重做，注意它还有跨坐标系比较带来的假阳性理论风险。
- `/JavaScript`、`/JS` 子串检测是有意从参考实现移植的朴素方案，categories.ts 已标注风险等级。
- `BG_LUMA = 240` 固定阈值假设白底：深色主题文档里合法的近白文字会被标为 strong signal。继承自参考实现，可在文案/FAQ 里说明这一局限。

## 观察（无证据支撑的意见，仅供参考）
- `white-font-resume-trick.md:23` 等处对 ATS/AI 简历解析行为的断言无出处，与同文可对照 PDF 规范验证的部分相比显得像既定事实，建议加限定词。
- 自然的下一批文章选题：PDF 元数据/XMP 隐藏（做「本扫描器不查什么」的诚实姿态）、发布前自查清单（面向作者）、面向 AI pipeline 构建者的防御文（可与现有三篇自然互链）。

- ReportView 的 verdict 文案（"A clean structural scan is not proof of safety…"）是很好的诚实对冲，重构时保留。
